## 1. 目標與範圍

### 1.1 目標
做一套給台灣中小企業(買賣業為主、預留輕製造)使用的 ERP,把「採購 → 庫存 → 銷售 → 應收應付 → 會計」串成一條資料不重打的流程,並且:

- 每張單據都可追溯(誰、何時、從哪張單轉來、改了什麼)
- 庫存數量與成本隨時正確,可以月結、可以重算
- 業務單據過帳後自動產生會計傳票
- 權限可細到「功能 × 動作 × 資料範圍(部門/倉庫)」

### 1.2 前提假設(若不符請告訴我,會影響設計)
| 項目 | 假設 |
|---|---|
| 產業 | 買賣業(進貨、銷貨、庫存),第二期再加 BOM/工單 |
| 規模 | 單一公司、多倉庫、使用者 < 200 人、單據量每日數千張以內 |
| 地區 | 台灣:新台幣為本位幣、營業稅 5%、統一編號、電子發票 |
| 部署 | 自架(Docker),內網或雲端 VM 皆可 |
| 多公司/多租戶 | 第一期不做,但資料表預留 `company_id` |

### 1.3 不在範圍(第一期)
人資薪資、CRM 行銷自動化、POS、電商前台、BI 自助分析、行動 App。

## 2. 決策(已定案 2026-10-07)

D1 由使用者指定;D2–D7 使用者授權由我決定,採原建議。D8–D10 是改用 PostgreSQL 後的連帶決定。

| # | 問題 | 決定 | 理由 |
|---|---|---|---|
| D1 | 技術棧 | **Go + Vue 3 + PostgreSQL**,全部以 docker compose 啟動 | 使用者指定 |
| D2 | 存貨成本法 | **月加權平均** | 台灣中小企業最常用、稅務可接受 |
| D3 | 第一期做總帳/傳票 | **做** | 自動拋轉傳票是 ERP 與「進銷存」的分水嶺 |
| D4 | 電子發票 | 第一期只做發票欄位與手動登錄;串接加值中心延到第二期 | 串接需申請與測試環境,不擋主流程 |
| D5 | 多幣別 | 外幣報價/採購 + 匯率表,帳上以本位幣(TWD)入帳 | |
| D6 | 負庫存 | **預設不允許**,可依倉庫用系統參數開啟 | |
| D7 | 單據修改 | 已核准單據不可直接改,只能「反核准」或「作廢重開」 | 保留完整稽核軌跡 |
| D8 | 非同步工作 | **River**(以 PostgreSQL 為佇列),不用 RabbitMQ | 可與業務資料**同一交易**寫入工作(過帳成功才一定會拋傳票),少一個服務 |
| D9 | 資料存取 | **pgx/v5 + sqlc**(手寫 SQL 產生型別安全的 Go 程式碼),不用 ORM | ERP 報表與過帳 SQL 複雜,需精準控制鎖與交易 |
| D10 | Redis | 第一期**不用** | 單號用 DB 列鎖、Refresh Token 存 DB 即可;真有快取需求再加 |
| D11 | 登入憑證 | access token(JWT,15 分)只放前端記憶體;refresh token 放 HttpOnly + SameSite=Strict cookie(7 天),每次刷新輪替;已撤銷的 token 超過 30 秒寬限仍被使用即視為竊用,撤銷整串 | 防 XSS 竊取 token、防 CSRF;30 秒寬限避免多分頁同時刷新被誤判 |
| D12 | access token 失效 | `users.token_version`(改密碼/停用/重設密碼時 +1)寫進 JWT,每個請求查 DB 比對 | 停用或改密碼立即生效;不用 `iat` 比對是因為 JWT 時間只到秒,會誤殺剛發的新 token |
| D13 | 權限點定義 | 權限點寫在程式碼(`internal/system/permission`),DB 只存角色擁有的代碼 | 權限點跟著功能程式一起版本控制,不會出現 DB 有、程式沒有的權限 |
| D14 | 防止提權 | 非超級管理員只能授予/移除自己擁有的權限,不能設定比自己大的資料範圍,不能修改超級管理員 | 只有「使用者管理」權限的人不能把自己升級成管理員 |
| D15 | 稽核寫入方式 | 在 service 層、同一交易內呼叫 `audit.Record`(不是 HTTP 中介層) | 需要修改前後的完整資料;業務回滾時稽核一併回滾 |
| D16 | 整合測試資料庫 | 每個測試建立暫存資料庫 `erp_test_<隨機>`、套用 migration、結束即刪 | 稽核日誌不可刪,無法在共用的開發庫清測試資料 |
| D18 | 限流 | 中介層 `platform/ratelimit`:已登入以使用者 ID 計算(預設 600 次/分);登入、刷新以 IP 計算(IPv6 以 /64),額度分開(預設 60、300 次/分);超過回 429 + `Retry-After`;前端刷新遇 429 不登出;記憶體內 token bucket,key 上限 10 萬 | 以使用者計算可避免同一 NAT 後的多人互相影響;刷新在每次整頁載入都會發生,不可與登入共用額度;單一 api 實例足夠,多實例時再改共享儲存 |
| D19 | 客戶/供應商結構 | 分成兩張表;聯絡人、地址存 JSONB 陣列 | 開單時把選到的地址複製進單據即可,不需關聯查詢;同一家公司既是客戶又是供應商時各建一筆 |
| D20 | 客戶資料範圍 | 依「負責業務」:本人=自己負責、本部門=負責業務在同部門;未指定負責業務的客戶只有「全部」看得到;新增/修改時負責業務也必須在自己範圍內 | 業務只看自己的客戶是最常見需求;不限制指派對象的話,可藉改負責人把客戶移出或塞進別人範圍 |
| D21 | 信用額度權限 | 獨立權限 `masterdata.customer.credit`;沒有權限的人新增時額度須為 0、修改時不可變動 | 信用額度是風險控管,不應由負責該客戶的業務自行調整 |
| D22 | 下拉選單資料 | 單位、分類、倉庫、稅別、付款條件、幣別、使用者清單(精簡欄位)只需登入即可讀取 | 開單的人需要選它們,卻不一定有維護基本資料的權限 |
| D23 | 幣別 | ISO 幣別為全系統共用表;匯率依公司、幣別、日期;查詢取「該日或之前最近一筆」 | 不必每天都輸入匯率 |
| D24 | 料品基本單位 | M1 允許修改;M2 起有庫存異動的料品禁止修改基本單位 | 改基本單位會讓歷史數量失真 |
| D25 | 庫存單據結構 | 調整、調撥、盤點共用 `stock_documents` / `stock_document_lines`,以 `doc_type` 區分,CHECK 約束各類型必填欄位 | 三者流程、狀態、權限相同,共用可省大量重複程式並讓畫面一致 |
| D26 | 庫存過帳核心 | `inventory.Post / Reverse` 寫流水帳並更新現有量;依 (料品, 倉庫) 排序後 `SELECT … FOR UPDATE`;同 key 先合計再判斷負庫存;反過帳寫反向分錄(沿用原單據日期) | 進貨、出貨等模組共用同一套規則;一致的上鎖順序避免死結;反向分錄保留稽核軌跡 |
| D27 | 盤點凍結 | 盤點單建立即快照帳面數,並在過帳或作廢前凍結該倉庫所有庫存異動;盤點明細只能新增不能刪除 | 盤點期間有進出會讓差異失真;可刪明細就能藏盤虧 |
| D28 | 單據明細單位 | 明細保存輸入單位、數量、當下換算倍數快照與基本單位數量 | 料品日後修改換算倍數不影響歷史單據 |
| D29 | 流水帳可改欄位 | 只允許回寫 `unit_cost`(M7 月結),其他欄位與刪除由 trigger 禁止 | 月結需回寫成本,其餘一律不可竄改 |
| D30 | 採購單狀態 | 不過帳;核准後可「結案」(剩餘未交視為取消),結案可「重開」回已核准;已有未作廢進貨單時不可取消核准 / 作廢。交貨狀態(未交 / 部分 / 交齊)為計算值,不自動改狀態 | 短交是常態,用結案表達;不自動結案可避免反過帳時狀態要倒回 |
| D31 | 進貨與退出單 | 共用 `goods_receipts`(doc_type receipt / return);明細 `po_line_id`(進貨引用採購明細)或 `receipt_line_id`(退出引用進貨明細),也可不引用 | 兩者欄位與流程相同,只差方向 |
| D32 | 已交量 / 已退量 | 不存累計欄位,以「已過帳」單據即時加總;開單時先檢查,過帳時依 id 順序鎖定來源單據後再檢查一次 | 沒有累計欄位就不會不同步;鎖來源單避免兩張單同時過帳超交 / 超退 |
| D33 | 採購金額 | 單價為原幣未稅;行金額依幣別小數位捨入,稅額依單頭合計計算;本位幣未稅 = 各行本位幣金額合計(與入庫成本一致);匯率為單據快照,未指定時取單據日期匯率 | 與台灣發票計稅方式一致;成本與應付金額可對得起來 |
| D34 | 應付帳款 | 進貨 / 退出過帳時產生(退出為負數),反過帳時刪除;已有沖帳則不可反過帳。表放在 finance 模組 | 應付是過帳結果,反過帳回到未過帳狀態;M5 付款沖帳接續 |
| D35 | 退出與未交量 | 進貨退出不回補採購單未交量 | 退貨是否補貨由採購另行開單決定,避免自動行為 |
| D36 | 入庫成本 | 流水帳 `unit_cost` = 明細本位幣金額 ÷ 基本單位數量;服務類明細不入庫但計入應付 | 供 M7 月加權平均使用 |
| D37 | 報價單與訂單 | 共用 `sales_orders`(doc_type quotation / order),皆不過帳、沿用 D30 的結案 / 重開;訂單可記錄來源報價單,報價轉訂單為整張複製,不追蹤報價數量 | 報價與訂單欄位幾乎相同;報價常改量改價,追蹤數量意義不大 |
| D38 | 銷售單據資料範圍 | 單據保存負責業務快照(取自客戶),依 D20 的規則過濾;範圍外單據視為不存在(404);開單時客戶須在自己範圍內;應收帳款依客戶目前負責業務過濾 | 業務只看自己的單據;用快照避免客戶改負責人時舊單據跟著搬家 |
| D39 | 可用量與信用額度 | 可用量 = 現有量 − 其他已核准訂單未出貨量,只提示不阻擋(允許缺貨接單,實際出貨過帳時才擋負庫存);信用額度在訂單核准時檢查:未沖應收 + 其他已核准訂單未出貨含稅金額 + 本單 ≤ 額度,超過即擋,並鎖定客戶列避免同時核准 | 缺貨接單是買賣業常態;信用風險在接單時就要控制 |
| D40 | 發票號碼 | 第一期手動登錄於出貨單,任何未作廢狀態皆可登錄 / 修改;格式 2 碼英文 + 8 碼數字;同公司未作廢單據不可重複 | 開票常晚於出貨;電子發票(D4)延後 |
| D41 | 採購 / 銷售共用 | 後端 `internal/trade`(單頭驗證、計價、訂單狀態轉換)、前端 `views/trade/TradeEditView` + `flows.ts`(各流程差異設定) | 四種流程規則相同,避免兩份幾乎一樣的程式各自分歧 |
| D42 | 收款單與付款單 | 共用 `settlements`(side receipt / payment),過帳時沖銷應收 / 應付的 `paid_amount`,反過帳還原;流程同過帳類單據(草稿 → 待審 → 已核准 → 已過帳),收款單依客戶負責業務套用資料範圍(D38) | 兩者流程與欄位相同,只差對象與權限 |
| D43 | 沖帳規則 | 一張單可沖多筆帳款、可部分沖;單一對象、單一幣別;每行金額與該帳款未沖餘額同號且不超過餘額,所以退回 / 退出的負數帳款可與正數互抵,合計不可為負;過帳時鎖定帳款後重新檢查,同一筆帳款被兩張單同時沖不會超沖 | 台灣中小企業常見「貨款扣除退貨」收付款;鎖帳款避免重複沖 |
| D44 | 沖帳與來源單據 | 草稿以上(未作廢)的收付款單引用某筆帳款時,來源單據不可反過帳;作廢的收付款單明細隨帳款移除(單據本身與稽核日誌保留) | 避免帳款被刪後沖帳單懸空 |
| D45 | 對帳單與帳齡 | 對帳單單一對象單一幣別:期初 + 帳款 − 已過帳收付款 = 期末;帳齡以本位幣、依到期日分組(未到期 / 1–30 / 31–60 / 61–90 / 90+),餘額為「目前」未沖餘額,不回推歷史;外幣收付款暫不計匯兌損益 | 先滿足催收與對帳;回推歷史餘額與匯兌損益留待總帳(M7)一併處理 |
| D46 | 傳票拋轉方式(調整 D8) | 進貨 / 出貨 / 收付款過帳時,**在同一個資料庫交易內同步**產生已過帳傳票(`gl.PostSource`),反過帳同交易內產生沖銷傳票(`gl.ReverseSource`),不經 River 佇列;River 保留給 M7 的背景工作(清理 token、月結) | D8 選 River 的理由是「過帳成功才一定有傳票」,同步寫入在同一交易內更直接地達成,且沒有「已過帳但傳票尚未產生」的空窗與失敗重試問題 |
| D47 | 拋轉規則 | `account_mappings` 以程式定義的 key(進貨存貨 / 費用 / 進項稅額 / 應付、銷貨應收 / 收入 / 銷項稅額 / 退回、收付款現金 / 銀行)對應科目,預載台灣常用科目,可在畫面調整,只影響之後產生的傳票;科目被規則使用時不可停用或改彙總 | key 固定才能保證程式一定找得到科目,科目本身仍可自訂 |
| D48 | 傳票不可改 | 自動拋轉傳票一律直接已過帳;手動傳票草稿 → 過帳(借貸須平衡)→ 可沖銷;已過帳 / 作廢的傳票與分錄由資料庫 trigger 禁止修改刪除,更正一律產生借貸相反、沿用原日期的沖銷傳票(一張傳票最多被沖銷一次);自動傳票只能由來源單據反過帳沖銷 | 會計紀錄不可竄改,與庫存流水帳(D26)同一套思路 |
| D49 | 會計期間關帳 | 以月為單位,沒有紀錄視為開放;關帳後該期的單據過帳 / 反過帳(含不產生傳票的庫存單據)與傳票新增 / 過帳一律被擋,重開後恢復;關帳需該期沒有草稿傳票、不可關未來月份;關帳以排他鎖、各檢查以共享鎖序列化 | 計畫要求「關帳後該期不可再新增 / 修改單據」;草稿單據仍可存在,但不能過帳 |
| D50 | 銷貨成本與期初 | M6 只拋收入與稅額,銷貨成本與庫存調整 / 盤點的傳票於 M7 月結(月加權平均)後拋轉;M6 之前已過帳的單據不補傳票,期初科目餘額由 M7 匯入 | 成本要月結才算得出來;避免對歷史資料產生不可驗證的傳票 |
| D51 | 月結成本 | 月加權平均,以「料品」為單位(跨倉庫,調撥數量互抵不影響成本):平均成本 = (期初金額 + 本月進貨金額)÷(期初數量 + 本月進貨數量),進貨金額取流水帳單位成本;出貨、銷貨退回、盤點、調整都以平均成本計價;期末金額 = 期末量 × 平均成本;整月無異動則整筆沿用期初。結果存 `item_costs`,同時是下月期初。產生兩張傳票(月底日期):銷貨成本(借 銷貨成本 貸 存貨)、存貨盤損益;並把平均成本回寫到沒有成本的流水帳(進貨保留原單位成本) | 實踐 D2;回寫只動 `unit_cost`(D29 允許) |
| D52 | 月結的順序與鎖定 | 只能結已結束的月份、須由最早有庫存異動的月份依序進行;月結後該月任何庫存異動(含進貨 / 出貨過帳、反過帳、庫存單據)被擋;只能取消最新一個月的月結(沖銷成本傳票、刪除結果、解鎖),之後可重算;月結 / 取消以公司列排他鎖、庫存異動以共享鎖序列化 | 成本一旦定案就不能被後來的異動悄悄改變;取消只限最新月避免中間月份失去基礎 |
| D53 | 對帳檢查 | 存貨(最近月結期末金額 vs 存貨科目月底餘額)、應收 / 應付(未沖餘額子帳 vs 總帳)、庫存現有量 vs 流水帳、已過帳傳票借貸平衡、未月結月份提醒;金額差異容許每筆 1 元四捨五入 | 讓月結後能一鍵確認帳與帳對得起來;M6 以前無傳票的單據造成的差異會被指出,匯入期初後消除 |
| D54 | Excel 匯入 | 後端以 excelize 讀 .xlsx(5MB、5000 列上限);**先預檢再匯入**:預檢列出全部錯誤(列號 + 欄位 + 原因,不寫入),通過才寫入,任何錯誤整批不寫入(單一交易);範本由系統產生(標題列 + 說明頁 + 範例頁),標題列不可改。類型:料品、客戶、供應商(已存在的代號視為錯誤,不覆蓋)與期初庫存、期初應收、期初應付、期初科目餘額;權限 `system.import.run`,寫稽核 | 匯入是上線最容易出錯的環節,先看完所有問題再一次修好,比邊匯邊失敗好;不覆蓋避免誤改既有資料 |
| D55 | 期初資料處理 | 須指定期初日期;期初庫存以 `opening_stock` 寫流水帳(只能用於尚無庫存異動的料品;月結成本時視同進貨,以單位成本計價);期初應收 / 應付以 `opening` 建立未沖帳款(可照常收付款沖帳,單據號碼同對象不可重複,外幣匯率空白取當日匯率);期初科目餘額產生一張已過帳傳票 `opening_balance`(借貸須相等、一次只能有效一批);三者靠「對帳檢查」確認一致。期初庫存 / 應收 / 應付 / 科目餘額可整批撤銷(已沖帳、已月結、期間已關帳者擋下);主檔不支援整批撤銷 | 期初金額分三處匯入(庫存、子帳、總帳),需要一個可驗證一致的機制;可撤銷讓上線前能重來 |
| D56 | 首頁儀表板 | 單一 `GET /dashboard`,**每張卡片只在使用者有對應權限時才計算並回傳**(沒有權限為 null),銷售與應收依資料範圍(D38)、待審只列使用者有核准權限的類型;卡片:銷售(今日 / 本月 / 近 7 天)、待處理單據、庫存警示、應收 / 應付(含逾期、7 日內到期)、月結提醒;金額與應收應付頁、帳齡口徑一致(退回 / 退出的負數帳款計入未沖餘額)。列表頁支援 `?status=` 預先篩選,儀表板連結直達 | 不同角色看到不同首頁;權限在後端判斷,不靠前端隱藏 |
| D57 | 併發與效能 | 以 `make perf-*` 在獨立資料庫量測約一年規模資料;併發正確性用「確定性鎖測試」(先手動持有鎖、驗證請求被擋)補足靠碰撞的併發測試,並以突變測試驗證;連線強制自訂計畫(避免選填篩選查詢退化);訂單類列表先分頁再算狀態;待審 / 草稿 / 已核准 / 未沖清用部分索引。細節與數據見 `doc/perf.md` | 數字說話:30 併發吞吐量 +49%、待審計數 -97%;鎖是否必要要用能穩定失敗的測試證明,不能只靠「看起來通過」 |
| D58 | 正式環境部署 | 單機 Docker Compose(`docker-compose.prod.yml`,與開發用完全分開):資料庫不對外開埠、api 唯讀檔案系統並移除所有 capability、日誌輪替、固定內部網段(讓 `TRUSTED_PROXIES` 有依據);TLS 由前面另外一層提供(cookie 帶 `Secure`,沒有 HTTPS 無法登入);備份用 `pg_dump` 自訂格式 + 腳本(寫暫存檔並驗證可讀才改名、依天數清理),還原提供 `--verify` 在暫存資料庫驗證;migration 以一次性 `migrate` 服務先跑完 api 才啟動;維運指令(建立管理員、清理 token)打包進映像的 `cli`。CI 驗證 compose 設定與映像內容 | 中小企業單機夠用且易於理解;高可用與水平擴充列為已知限制(限流為單程序記憶體,只能跑一個 api) |

| D60 | 營業稅 401 申報資料 | 依申報期別(雙月)即時彙總已過帳的出貨 / 銷貨退回 / 進貨 / 進貨退出,本位幣,退回與退出以負數沖減;**銷項以發票日期為準、必須已登錄發票號碼**,進項以單據日期為準、**必須有供應商發票號碼才可扣抵**;沒有發票號碼者不計入,改列「待處理」避免漏登而不自知;應稅依買方有無統編分三聯式 / 二聯式,零稅率與免稅分列;進貨依料品類型拆「進貨」與「費用及其他」;產出彙總、銷項明細、進項明細、待處理四個工作表的 Excel;權限沿用 `gl.report.read`,不套業務資料範圍(會計報表為全公司) | 只做「申報參考數字」:不含上期留抵、扣抵比例、海關代徵、固定資產進項,也**不產生財政部媒體申報檔**(格式需對照官方規格另行驗證,不憑記憶實作) |
| D61 | 多層簽核 | 規則依單據類型(採購單、進貨、報價 / 訂單、出貨、收款、付款)與本位幣含稅金額決定:**第 1 層永遠是具該單據核准權限的人(與原本相同),規則只追加第 2 層以後要指定的角色**(最多 5 層),所以沒有規則的單據完全維持舊行為;**送審時把流程快照到 `document_approvals`**,之後改規則不影響進行中的單據;核准時完成目前層級,還有後續層級就維持待審(不改單據狀態、版本不變),最後一層才真正核准;退回 / 取消核准 / 作廢清除流程;**同一個人不可核准同一張單據的兩個層級**(超級管理員也一樣,避免單人繞過);超級管理員可越過「角色」限制但不可越過同人限制;規則建立時檢查角色須具備該單據的核准權限(否則該層永遠沒人能核准);被規則使用的角色不可刪除;每次分層核准都記稽核 | 引擎集中在 `internal/approval`,各單據動作處理只加一個呼叫;庫存單據(調整 / 調撥 / 盤點)沒有金額概念,本版不納入;不做「會簽 / 或簽」、依部門或業務分流、代理人 |

| D63 | 批號與效期 | 料品設定「批號管理」:不管理 / 批號 / 批號與效期,**有庫存異動後不可改**(舊異動沒有批號)。批號主檔以 (公司, 料品, 批號) 為唯一,**批號一律轉大寫、不含空白**,一個批號只有一個效期(同批號再入庫效期不同會被擋)。**集中在庫存引擎 `apply()` 處理**:各單據只在明細多帶批號與效期,引擎展開成逐批號的分錄並維護 `inventory_lot_balances`(各批號合計必等於料品現有量,對帳檢查會核對)。規則:入庫批號必填、新批號須效期;出庫可指定批號,**空白則先到期先出**(沒有效期的排最後),可能拆成多筆分錄;**批號庫存不可為負,即使倉庫允許負庫存**;**出貨不可出已過期批號**,先到期先出時略過過期批號(庫存不足的訊息會說明有過期庫存),報廢(調整)、調撥、沖銷、進貨退出不受效期限制;調撥沿用批號;沖銷沿用原分錄的批號;盤點對批號管理的料品每個批號一行,帳面快照依 (料品, 批號);銷貨退回須指定退回的批號,進貨退出預設沿用被退進貨明細的批號。批號庫存、追溯(供應商 / 客戶,客戶依資料範圍)與儀表板效期警示(30 天內到期與已過期) | 先到期先出(FEFO)而非先進先出,是食品 / 藥品 / 化妝品等有效期商品的通用做法;成本仍依料品月加權平均,不做批次成本;不做序號管理、不做批號屬性(產地、檢驗)、不做保留 / 預留批號、不做依批號的銷售限制 |
| D17 | API 型別 | 第一期前端型別先手寫(`src/api/*.ts`),OpenAPI 產生延後 | 目前 API 數量少,導入產生器的成本大於效益;API 穩定後再評估 |

## 4. 系統架構

```
 ┌─────────────┐  HTTPS  ┌───────────────────────┐
 │ Vue 3 SPA   │────────▶│ nginx(web 容器)      │
 └─────────────┘         │ 靜態檔 + /api 反向代理 │
                         └──────────┬────────────┘
                                    │ /api
                             ┌──────▼───────┐
                             │ Go API (Gin) │──┐ 同一交易寫入業務資料 + River 工作
                             └──────┬───────┘  │
                             ┌──────▼──────────▼──┐      ┌──────────────┐
                             │ PostgreSQL 18       │◀────▶│ Go Worker    │
                             │ (業務資料 + River)  │      │ 拋傳票/月結/ │
                             └─────────────────────┘      │ 匯出/通知    │
                                                          └──────────────┘
```

**後端分層(模組化單體 Modular Monolith)**:每個業務模組自成一個 package,內部分 `handler → service → repository`;模組之間只透過 service 介面或領域事件互動,不跨模組直接查別人的表。日後真要拆服務也有清楚邊界。

## 5. 功能模組

標記:**P1** 第一期(MVP)、**P2** 第二期、**P3** 之後

### 5.1 系統基礎(P1)
- 登入、JWT + Refresh Token、密碼政策、登入失敗鎖定、(P2)2FA
- 組織:公司、部門、員工
- 權限:RBAC(角色 → 權限點 `模組.資源.動作`)+ 資料範圍(全部/本部門/本人/指定倉庫)
- 稽核日誌:所有寫入動作記錄 before/after
- 單號規則:可設定前綴 + 日期 + 流水號(如 `PO202610070001`),以序號表 `SELECT ... FOR UPDATE` 保證不重號
- 系統參數、代碼表(付款條件、運送方式…)
- 附件上傳(單據可掛檔)
- 簽核流程:(P1)單層核准;(P2)多層、依金額分流
- 通知:站內通知;(P2)Email / LINE

### 5.2 基本資料(P1)
- 料品:料號、品名規格、分類、單位與**單位換算**(箱/個)、條碼、安全庫存、預設倉、稅別、啟用狀態
- 客戶 / 供應商:統編、聯絡人、多地址、付款條件、信用額度(客戶)、幣別
- 倉庫、儲位(P2)
- 幣別、匯率表(依日期)
- 稅別(應稅 5%、零稅率、免稅)
- 價格表:客戶價、數量折扣(P2)

### 5.3 採購(P1)
請購單(P2)→ **採購單** → **進貨單**(可部分進貨)→ **進貨退出單**
- 採購單核准後才能轉進貨;追蹤未交量
- 進貨單過帳:增加庫存、產生應付、拋轉傳票
- 報表:採購明細、未交貨清單、供應商進貨統計

### 5.4 銷售(P1)
報價單 → **訂單** → **出貨單**(可部分出貨)→ **銷貨退回單**
- 訂單檢查:信用額度、可用庫存(在庫 − 已保留)
- 出貨過帳:扣庫存、產生應收、計算銷貨成本、拋轉傳票
- 發票:P1 手動登錄發票號碼;P2 串接電子發票開立/作廢/折讓
- 報表:銷售明細、未出貨清單、客戶/業務/品項銷售排行、毛利分析

### 5.5 庫存(P1)
- **庫存異動流水帳**(唯一真相來源):所有進出都寫一筆,現有量是彙總結果
- 庫存調整單、倉庫調撥單、盤點單(盤點凍結 → 輸入實盤 → 產生差異調整)
- 批號 / 效期(P2)、序號(P3)
- 成本:月加權平均;**月結**計算單位成本、回寫銷貨成本;可重算
- 報表:現有庫存、收發存明細、庫存週轉、呆滯料、安全庫存不足

### 5.6 應收應付(P1)
- 應收帳款:由出貨/退回產生;收款單沖帳(可一筆收款沖多張、部分沖)
- 應付帳款:由進貨/退出產生;付款單沖帳
- 票據管理:應收/應付票據、到期兌現(P2)
- 對帳單、帳齡分析

### 5.7 會計總帳(P1 基本、P2 完整)
- 會計科目表(預載台灣常用科目,可自訂)、輔助核算(部門、客戶、供應商)
- 傳票:手動傳票 + 業務單據**自動拋轉**(依「拋轉規則」設定借貸科目)
- 傳票過帳、期間關帳(關帳後該期不可再新增/修改單據)
- 報表:日記帳、總分類帳、試算表、(P2)資產負債表、損益表
- (P2)營業稅 401 申報資料匯出

### 5.8 生產(P2)
BOM(多階)、工單、領料、完工入庫、(P3)MRP 需求計算

### 5.9 報表與儀表板(P1 基本)

## 6. 核心單據流程

```
採購: 採購單 ──核准──▶ 進貨單 ──過帳──▶ [庫存 +] [應付 +] [傳票: 存貨/進項稅額 ⇄ 應付帳款]
                                         │
                                  付款單 ─┴─沖帳─▶ [傳票: 應付帳款 ⇄ 銀行存款]

銷售: 訂單 ──核准──▶ 出貨單 ──過帳──▶ [庫存 −] [應收 +] [傳票: 應收帳款 ⇄ 銷貨收入/銷項稅額]
                                       │                [傳票: 銷貨成本 ⇄ 存貨](月結回寫)
                                收款單 ┴─沖帳─▶ [傳票: 銀行存款 ⇄ 應收帳款]
```

**單據狀態機(所有單據共用)**

```
草稿 ──送審──▶ 待審 ──核准──▶ 已核准 ──過帳──▶ 已過帳 ──(下游全結)──▶ 已結案
  ▲             │ 退回           │ 反核准(無下游時)   │ 反過帳(未關帳且無下游時)
  └─────────────┘                ▼                   ▼
                              作廢(保留紀錄,不可刪除)
```

## 7. 資料模型關鍵設計

1. **單據頭 / 單據身**:`xxx_orders` + `xxx_order_lines`;單身記錄 `source_type / source_id / source_line_id`,追溯上游單據與未轉量。
2. **金額與數量**:一律 `NUMERIC`(金額 `NUMERIC(18,4)`、數量 `NUMERIC(18,4)`、單價 `NUMERIC(18,6)`),Go 端用 `shopspring/decimal`,**禁止 float**。
3. **捨入規則**:單身金額先四捨五入到小數 0 位(新台幣),稅額依單頭合計計算,規則集中在一個套件。
4. **多幣別**:單據存原幣金額 + 匯率 + 本位幣金額。
5. **庫存**:`inventory_transactions`(流水帳,只增不改)+ `inventory_balances`(料品×倉庫現有量,過帳時 `SELECT ... FOR UPDATE` 更新)。
6. **併發控制**:主檔與單據使用 `version` 欄位做樂觀鎖;過帳使用交易 + 列鎖。
7. **刪除策略**:主檔停用不刪;單據只能作廢;草稿可實刪。
8. **稽核**:共用欄位 `created_by / created_at / updated_by / updated_at`,另有 `audit_logs` 存 JSON diff。
9. **多公司預留**:主要表帶 `company_id`,查詢層統一加條件。
10. **時區**:時間欄位用 `TIMESTAMPTZ`、連線時區固定 UTC,顯示 Asia/Taipei;單據日期(`doc_date`)用 `DATE`,與建立時間分開。
11. **主鍵**:`BIGINT GENERATED ALWAYS AS IDENTITY`;`updated_at` 由共用 trigger `set_updated_at()` 維護。
12. **列舉狀態**:用 `VARCHAR` + `CHECK` 約束,不用 PostgreSQL `ENUM`(新增值較麻煩)。

## 8. API 與程式規範

- RESTful,路徑 `/api/v1/{module}/{resource}`;狀態變更用動作端點,例如 `POST /api/v1/purchase/orders/{id}/approve`
- 統一回應格式 `{ "data": ..., "meta": {分頁}, "error": {code, message, details} }`
- 錯誤碼分模組(`PUR-001`、`INV-003`),前端依碼顯示中文訊息
- 列表 API 統一支援分頁、排序、篩選參數
- 所有寫入 API 需權限檢查中介層 + 稽核中介層
- 冪等:過帳/付款等關鍵動作支援 `Idempotency-Key` header
